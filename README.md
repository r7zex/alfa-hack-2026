# Делора · Alfa Hack 2026

Демонстрационный кредитный кабинет для ИП и ЮЛ: подбор → заявка и PDF → фоновая проверка → автоматическое или ручное решение → встречные условия → код подписи → демо-выдача → кредит и график. PostgreSQL хранит пользователей, документы, очередь, историю, сообщения, уведомления и сделки. Источники синтетические; деньги не переводятся. Новостная лента не входит в продукт.

## Запуск

Требуются Docker и Compose v2. Существующий `.env` сохраните.

```bash
cp .env.example .env  # только если файла ещё нет
# Измените DB_PASSWORD; для локальной демонстрации включите:
# DEMO_AUTH_ENABLED=true
# DEMO_SIGNING_CODE_VISIBLE=true
# DEMO_SIGNING_CODE_VISIBLE показывает синтетический код прямо в кабинете.
docker compose up --build -d
docker compose ps
docker compose exec app python -m app.seed
```

Открыть [кабинет](http://127.0.0.1:8000), [OpenAPI](http://127.0.0.1:8000/docs). API применяет Alembic перед запуском; worker стартует после readiness API. Образ содержит реальные проверенные native-веса LightGBM. Датасет, Redis, внешние API и Qwen для основного процесса не нужны. `docker compose down` сохраняет PostgreSQL volume. Не применяйте `down -v` к сохранённым данным.

Seed повторяемый, не очищает БД и не меняет существующие пароли/заявки. Кнопка «Демо-сценарии» открывает 12 синтетических компаний. Есть отдельный сотрудник без подписи. Банковские роли доступны кнопками «Аналитик», «Согласующий», «Демо: администратор». Для seed-аккаунтов `auto@demo.example.com`, `counter@demo.example.com`, `documents@demo.example.com`, `underwriter@demo.example.com`, `approver@demo.example.com`, `admin@demo.example.com` и остальных ключей сценариев используется **локальный синтетический** пароль `Delora-demo-2026!`. Не включайте демонстрационный вход в общей установке с реальными данными. Обычная регистрация/вход/смена пароля из main сохранены; создать обычного администратора: `python -m app.admin --help`.

## Что реализовано

- Сохраняемый конвейер: `data_check → enrichment → scoring → decision`. HTTP submit ставит задачу и быстро возвращает `submitted`; worker выполняет внешние/ML операции вне транзакции, а результаты фиксирует короткими транзакциями.
- PostgreSQL `SKIP LOCKED`, lease с fencing token, ограниченные попытки, backoff, восстановление после истечения lease. Уникальные submission, ML-результат, версия предложения, договор и выдача защищают от дублей.
- SSE с HttpOnly cookie, повторной проверкой сессии, Last-Event-ID и тремя подключениями на пользователя. При недоступности SSE остаются polling и ручное обновление.
- UNDERWRITER берёт заявку, решает в пределах лимита, запрашивает документы и передаёт на согласование; APPROVER решает крупные суммы и возвращает аналитику. ADMIN управляет версиями правил и сбоями, видит аудит и аналитику.
- Задачи с проверкой документов/ответов, отдельный чат с банком, непрочитанные сообщения, сохраняемые уведомления, приглашение сотрудника без права подписи.
- Полное встречное предложение: продукт, сумма, срок, ставка, причина, срок действия, отзыв. Старые версии сохраняются; устаревшее/истёкшее предложение принять нельзя.
- Код подписи привязан к подписанту и версии предложения: HMAC в БД, TTL, лимит попыток, одноразовость. Подписание демонстрационное, не SMS/УКЭП. Договор защищён SHA-256.
- Выданные кредиты: серверный Decimal-график, календарные месяцы, точный остаток, таблица/интерактивный график/CSV. Овердрафт возвращает основной долг последним платежом.
- Шесть независимых mock-источников: ЕГРЮЛ/ЕГРИП, ФНС, БКИ, финансы, обороты, регистрация выдачи. Администратор переключает сбои; данные и circuit breaker сохраняются в БД.
- Аналитика из БД: статусы, продукты, решения, очередь, ошибки, сумма выдач, время обработки, доля автоматических решений, историческая воронка и CSV.

## ML и кредитная политика

Предоставленный `LightGBM.joblib` пассивно разобран без `joblib.load`. В репозитории лежат извлечённые native-веса с проверенным SHA-256: 450 деревьев, binary objective, 24 признака. `FinancialFeaturesProvider` получает отдельный финансовый профиль с периодом, единицами и происхождением. Значения не восстанавливаются из суммы кредита, выручки и расходов анкеты. Синтетические профили явно помечены; при отсутствии признаков сохраняется `ML unavailable`, процесс продолжает отдельная демонстрационная политика.

Смысл исходного класса 1, единицы обучения, порог, калибровка и holdout-метрики не подтверждены. Поэтому выводится **технический score класса 1**, а не PD, риск банкротства или шанс одобрения. Вклады признаков сверяются с raw-score и не выдаются за причины кредитного решения. Правила отдельно учитывают документы, источники, возраст бизнеса, денежный поток, обязательства и лимит полномочий. Начатая обработка сохраняет свою версию правил.

Новый эксперимент обучения использует стандартный `LGBMClassifier(objective="binary")`, 70/15/15, подбор по validation AP и порога по validation F2; test используется после фиксации выбора. Focal Loss убран из основного обучения. Без исходного датасета новые метрики не заявляются. Подробнее: [model card](docs/model-card.md), [импорт весов](docs/imported-lightgbm.md), [ML API и обучение](docs/ml-scoring-mocks.md).

## Qwen 2.5 1.5B — опционально

```bash
docker compose -f compose.yaml -f compose.qwen.yaml up --build -d
docker compose -f compose.yaml -f compose.qwen.yaml logs -f qwen-init
```

Overlay включает Ollama, скачивает `qwen2.5:1.5b` и задаёт CPU-совместимые параметры. Первый запуск требует сети и около 1 ГБ весов. Основной сервис продолжает работать при отказе модели. Проверены реальные CPU-ответ и отказ на посторонний вопрос; генерация на проверенном сервере занимает минуты. Три этапа защиты: классификация запроса → ответ → независимая проверка ответа. Контекст собственной заявки передаётся только по явному согласию; PDF, пароли и чужие данные не передаются. [Настройка и ограничения](docs/ai-assistant.md).

## Проверки

```bash
python -m venv .venv
.venv/bin/pip install -r requirements-dev.txt -r requirements-ml.txt
.venv/bin/python -m pytest -q
node --test tests/frontend*.test.mjs
.venv/bin/ruff check app ml scripts tests --select E9,F63,F7,F82
.venv/bin/python scripts/check_secrets.py
```

PostgreSQL fixture пересоздаёт таблицы: задавайте `TEST_AUTH_DATABASE_URL` **только для отдельной одноразовой БД**. Для проверки обновления существующей схемы задайте отдельную пустую `TEST_MIGRATION_DATABASE_URL`, имя которой содержит `migration`. Проверяются аккаунт, сессия и черновик до/после upgrade.

```bash
.venv/bin/pip install -r requirements-e2e.txt
.venv/bin/python -m playwright install chromium
E2E_BASE_URL=http://127.0.0.1:8000 .venv/bin/python -m pytest -q tests/e2e_product.py
# Для реального Qwen дополнительно E2E_QWEN=1.
```

Дополнительные destructive QA-проверки своего worker/app/db находятся в `tests/e2e_worker_recovery.py` и включаются только явными E2E_ALLOW_* флагами для отдельного проекта.

E2E меняет только синтетические данные, но должен запускаться в отдельном Compose-проекте/volume. CI проверяет Python, JS, статический анализ, формы секретов, PostgreSQL, Alembic, Docker и A–G; реальный Qwen H проверяется отдельно. [Фактическая приёмка](docs/acceptance.md).

## Эксплуатация и документация

`/health` — процесс; `/ready` — БД и схема; `python -m app.worker --health` — heartbeat worker. Защищённые `/api/analyst/operations`, `/analytics` показывают очередь и метрики. Запросы получают X-Request-ID и JSON-лог без cookie, токенов, кодов и содержимого PDF. Секреты/рабочие файлы исключены из Docker context. Параметры worker, источников и подписи описаны в `.env.example`.

Новые миграции добавлены после прежнего head, текущий head `a2026c002002`; старые миграции main сохранены. Все изменения находятся в `feat/integrated-credit-pipeline`, без merge в main. Исторические демо-выдачи получают график идемпотентно, условия не переписываются; `completed` без факта выдачи не превращается в фиктивный кредит.
