# Авторизация и сессии

Регистрация создает аккаунт и новый профиль ИП/ЮЛ в одной транзакции, а затем
открывает сессию. Подключаться к чужому бизнесу по известному ИНН нельзя.
Почта приводится к нижнему регистру, ИНН проверяется по длине и контрольным цифрам.
Публичная регистрация всегда создает роль `client` и отвергает поле `role`.

Пароли хешируются Argon2 через pwdlib. В БД хранятся только SHA-256 хеши случайных
токенов сессии и CSRF. Токен сессии доступен браузеру как HttpOnly cookie,
SameSite=Lax, Path=/. Настройка `COOKIE_SECURE=true` обязательна при HTTPS.
Стандартный срок сессии - 7 дней без автоматического продления.
Каждый вход создает новый токен, а существующая сессия этого браузера отзывается.
Выход, отзыв сессии и смена пароля удаляют сессии из БД немедленно.
Смена пароля требует текущий пароль и завершает все сессии аккаунта.

POST/PATCH/DELETE с авторизацией требуют заголовок `X-CSRF-Token`.
Он возвращается при входе и регистрации; восстановить его можно через GET /csrf.
Сервер связывает CSRF-токен с конкретной сессией и проверяет Origin/Sec-Fetch-Site.
API возвращает Cache-Control: no-store. Лимиты запросов входа и регистрации
хранятся в БД и действуют между процессами: 30 запросов/мин на IP и 10 на почту
по умолчанию. Учитывается адрес, который ASGI-сервер считает адресом клиента;
заголовки прокси доверяйте только своему reverse proxy.

## API

Все пути имеют префикс `/api/auth`; схема и примеры доступны в `/docs`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | /config | Включен ли демо-вход |
| POST | /register | Регистрация ИП/ЮЛ, создание сессии, 201 |
| POST | /login | Вход по почте и паролю |
| GET | /me | Пользователь и его профиль бизнеса |
| GET | /admin/me | Проверка роли администратора |
| GET | /csrf | CSRF-токен текущей сессии |
| GET | /sessions | Список действующих сессий аккаунта |
| DELETE | /sessions/{id} | Отзыв собственной сессии, 204 |
| POST | /logout | Выход из текущей сессии, 204 |
| POST | /logout-all | Выход из всех сессий аккаунта, 204 |
| POST | /password | Смена пароля и отзыв всех сессий, 204 |
| PATCH | /profile | Сохранение профиля собственного бизнеса |
| POST | /demo | Синтетические аккаунты, только при явном включении |

401 означает отсутствие действующей сессии или неверные данные входа, 403 - запрет
по роли/CSRF, 409 - дубликат, 422 - некорректные поля, 429 - превышение лимита.
Для остальных продуктовых роутеров доступны `get_current_user`, `require_admin`,
`require_client` из `app/dependencies.py`; они читают пользователя и роль из БД.
Параметры user_id/business_id от клиента не заменяют проверку владельца в запросах.

## Запуск и обновление

После получения изменений:

```bash
git switch feat/auth
git pull origin feat/auth
docker compose up --build -d
```

Контейнер применит `alembic upgrade head` перед запуском Uvicorn. Новая миграция
`c49f08a2d316` продолжает существующую `1bd2be57b412`, добавляет таблицы
`auth_sessions`, `auth_rate_limits` и поля профиля. Существующие пользователи и
бизнесы сохраняются. Удалять volume PostgreSQL не нужно.

При локальном запуске без Docker:

```bash
python -m pip install -r requirements.txt
python -m alembic upgrade head
python -m uvicorn app.main:app --reload
```

Секрет БД берется из `.env`, пример настроек находится в `.env.example`.
Для HTTPS установите `COOKIE_SECURE=true`; на локальном HTTP оставьте false.
`DEMO_AUTH_ENABLED=false` по умолчанию. Для автономной демонстрации можно установить
true в `.env` и пересоздать контейнер приложения. Это открывает вход без пароля
в три синтетических аккаунта, включая админа; на публичном сервисе этот режим
нельзя использовать с настоящими данными.

## Администратор

```bash
docker compose exec app python -m app.admin --email admin@example.com
# Или при локальном запуске:
python -m app.admin --email admin@example.com
```

Пароль вводится скрыто дважды. Команда не повышает роль существующего пользователя.
После создания войдите через обычную форму с почтой и паролем. При выключенном
демо кнопка "Вход администратора" открывает эту форму, без обхода проверки пароля.
В демо-режиме кнопка открывает синтетический аккаунт; она не использует обычных
пользователей с совпавшей почтой.

## Проверка

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
node --test tests/frontend*.test.mjs
python -m alembic check
```

Auth-тесты используют настоящие SQL-запросы и временную SQLite. Для отдельной
проверки на PostgreSQL задайте `TEST_AUTH_DATABASE_URL` и запустите
`python -m pytest tests/test_auth.py -q`. Используйте исключительно отдельную
тестовую БД: fixture пересоздает таблицы.

Ручная проверка: зарегистрировать ИП и ЮЛ, обновить страницу, выйти и войти снова;
проверить неверный пароль, сохранение профиля, смену пароля и выход со всех
устройств; клиент должен получать 403 от `/admin/me`.
HTTP-примеры находятся в [auth.http](auth.http).

## Граница реализации

Аккаунты, пароли, бизнес-профиль и сессии сохраняются на сервере. Заявки, решения
по кредиту и документы текущего фронтенда пока остаются браузерной демонстрацией.
Их серверная реализация находится за пределами авторизации этой ветки.
Проверка личности, банковских полномочий, почты и отправка писем восстановления
пароля не имитируются. Для действующего банка потребуются отдельные интеграции.

## Результат проверки реализации

Проверены 40 Python-тестов и 13 JavaScript-тестов. В Chromium на экранах
1440x1000 и 390x844 проверены формы; на десктопе пройден сценарий регистрации,
обновления страницы, сохранения профиля, смены пароля, неверного и верного входа,
выхода и демо-входа. Ошибок JavaScript не обнаружено.
Через встроенный PostgreSQL PGlite проверены upgrade/check/downgrade Alembic
и 17 auth-тестов по PostgreSQL-протоколу. Нативный PostgreSQL 16 в Docker в этой
среде не запускался; проверка контейнерной сборки остается для обычного Docker-окружения.
